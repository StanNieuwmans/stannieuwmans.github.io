Azure DevOps,
without the hassle.

Dodo is a calm work layer on top of the Azure DevOps REST API. The same work items, shown one question per screen. You run it yourself, and your data never leaves Azure DevOps.

Status: pre-1.0. Dodo is built phase by phase and used every day, but things still change between versions. Read the release notes before you update.

Run it yourself View the source 
$ git clone https://github.com/StanNieuwmans/Dodo && cd Dodo && docker compose up -d

One command, only Docker needed. Then open localhost:3000 and sign in with a personal access token.

Not a replacement. A calmer front door.

Azure DevOps has everything a team needs, but it shows too much at once. Dodo reads and writes the same work items through the REST API and only shows what matters to you right now.

01

Calm by design

Every view answers one question. Optional things start collapsed, and things you can't use stay visible with the reason in text.

02

Azure DevOps stays the source

No data moves. Dodo works with your team's own process: state categories instead of hard-coded state names, and types straight from the API.

03

Confirm before changing

Bulk moves, the assistant and team-board rules show what will change before anything is written. Light actions come with Undo.

04

Keyboard and screen reader

Built to WCAG 2.2 AA. Everything works from the keyboard, dragging cards included: Space picks a card up, the arrow keys move it.

Everything a sprint needs, nothing more

Twelve phases in, Dodo covers the daily work of a Scrum team, from your own list to the team's way of working.

All release notes

My work

Your items, the ones you follow and your newest notifications on one page. You choose which blocks show.

A live sprint board

To do, In progress and Done by state category, story points per column, and quiet updates every 30 seconds while the tab is open.

Items you can actually read

One page per item with details, tasks, links, attachments, comments with @-mentions and linked pull requests. Edit, finish or delete in one go.

Blocked, at a glance

All blocked items of your team, grouped by how long they've been stuck. Ask someone for help or unblock with a note, right from the card.

Team boards

Build a board for one way of working, like intake or bug triage, with rules for what a drag does. Every publication is a version you can restore.

Command palette and shortcuts

Ctrl K finds any item by title or #number and runs any action. G then B opens the board, N makes a new item, ? lists the rest.

An assistant that asks first

Off by default. Bring your own key (Anthropic, OpenAI or Azure OpenAI) to ask questions with sources, draft tasks or summarize an item. Nothing changes without your confirmation.

Backlog and inbox

Select up to 50 backlog items and move them to a sprint in one step, with an overview first. The inbox collects mentions, assignments and changes to items you follow.

Light, dark, Dutch, English

Choose a theme or follow your computer. All of Dodo's own text exists in Dutch and English; what comes from Azure DevOps is shown as-is.

Your token stays yours

No central service, no database. A small server passes your calls to Azure DevOps and keeps nothing.

  • ✓Encrypted cookie. Tokens and AI keys never reach logs, files or browser JavaScript.
  • ✓Your permissions only. Work Items (read and write) is enough.
  • ✓One file exception. Team board layouts are saved on your server, never item text.

Deploying for an organisation

One config file for your whole organisation

Set how Dodo works for your whole organisation in a dodo.config.json: one file you keep in git, so every change is a reviewed commit and a new deploy. Environment variables still work, for secrets and as an emergency override.

  • ✓Default or locked. Each setting is either a default people can change, or locked for everyone and read-only in Settings.
  • ✓Read once at start. Dodo checks it against a schema. A broken file means Dodo won't start. The server never writes it.
  • ✓Variable first, then file, then default. Existing setups keep working, and a variable can override a locked value in an emergency.
  • ✓No secrets in the file. Passwords and keys stay environment variables, so the file is safe in git. On Railway you can paste it into one variable.
  • ✓See where a value comes from. The Diagnose page lists the active settings and their source.

How it's made

Built by AI agents, decided by a person, checked every phase

Claude agents write all of Dodo's code. They don't decide what Dodo is. Anything the spec, the decisions or the designs don't answer becomes a question for the product owner, and the answer is written down in the repo.

Agents plan the work, build it in small tasks and test it. A separate reviewer then tries to break each task before it is merged.

The check before every release

  • ✓Three testers. Build, types, lint and unit tests; end-to-end runs with an accessibility scan in Dutch and English, light and dark; and every "done when" criterion in the spec.
  • ✓Six reviewers. Correctness, security, spec, design, accessibility, and language and code quality.
  • ✓Every finding is checked again by a separate verifier before it counts.
  • ✓Only then a pull request, and CI on GitHub has to be green too.

Why “Dodo”?

It's short for DOod aan aDO, Dutch for “down with ADO”. A joke, and a promise: the hassle of working in Azure DevOps should disappear, the way the dodo bird did. Dodo doesn't replace Azure DevOps. It needs it, and it keeps every item there.
